# 全局规范（所有文档、所有项目通用的小规矩）

> **这是什么**：放「到处都用得上」的通用约定。规矩不多，**目前两条：时间戳、每步说清为什么**。
> **谁要遵守**：**我和 AI 都要遵守**。
> **位置**：知识库 给AI的规矩\全局规范.md（这套文件里）
> **谁会引用它**：个人记忆里的几张表、各项目的《项目更新日志.md》、程序生成的《给 AI 须知》——谁的记录带时间，谁就按它写。 里那个「给 AI 须知」的默认说明
> **以后再加规矩**：直接往下面「规范二、规范三……」加，格式照抄规范一的样子。

---

## 【给 AI 的必读说明】

1. 你写**任何带时间的记录**（个人记忆、项目更新日志、你自己的记忆条目），一律用下面**规范一**的格式。
2. **不许自己另发明格式**。看到 `2026/10/14`、`10-14`、单写 `18:56` 这类旧写法，**不要跟着抄**，一律改成规范格式。
3. 写之前**先取当前真实时间**，格式化成规范样子再落笔。**不知道就写「（补记）」，绝不许编一个假时间。**
4. 你每做一步，都要按**规范二**说清「为什么」—— 只报"做好了"不算完成汇报。

## 规范一：时间戳（全局统一格式）

**标准写法**

```
【2026-10-14 18:56】
```

拆开看：

| 部分 | 要求 |
| --- | --- |
| 外面的 `【 】` | 中文方括号 —— 这就是「精美」的地方，一眼能认出是时间戳 |
| 日期 | **四位年 - 两位月 - 两位日**，中间用**半角减号 `-`**（不写 `2026/10/14`） |
| 中间 | **一个空格** |
| 时间 | **24 小时制**，**精确到分钟**（`18:56`，不写「下午 6 点 56」） |

**什么时候多写「秒」**

只有一种情况：**同一天改了好几回、要分先后**，才写成 `【2026-10-14 18:56:30】`。平时不写秒。

**用在哪、怎么写**

| 用在哪 | 例子 |
| --- | --- |
| 个人记忆的表格（「日期时间」列） | `【2026-10-14 18:56】` |
| 项目更新日志的标题行 | `## 【2026-10-14 18:56】～18:57　铁匠新增「攻击力」强化` |
| AI 的记忆条目 | `【2026-10-14 18:56】……` |
| 只记得日期、时间记不清（补记） | `【2026-10-14】（补记）` |

**新旧怎么过渡**

- **以前写的老记录不动**（里面还是 `2026-10-14` 这种老格式），省得翻旧账、也免得改错。
- **从 2026-10-14 起，新写的记录一律用新格式** `【2026-10-14 18:56】`。

**统一了有什么好处**

- **好排序**：都是同一个格式，前后顺序一目了然。
- **好搜**：在「文档中心」里搜 `【2026-` 能把所有带时间的记录全翻出来。
- **好对照**：个人记忆和项目更新日志能对上「哪天学的东西、对应哪次改动」。

## 规范二：AI 每做一步，都要说清「为什么」

**一句话**：AI 每动一个地方（改代码、加功能、改文件、跑命令），都要用大白话告诉我 **为什么这么做**，**不能只丢一句"做好了"**。

**必须交代这三件事**

| 要交代什么 | 例子 |
| --- | --- |
| **为什么做**（起因是谁提的、什么问题） | 「因为你反馈任务栏图标是默认的，不好看」 |
| **为什么这么做**（选它的理由、排除了什么） | 「查到根因是『窗口图标』没设 —— 它和『文件图标』是**两回事**，所以只换文件图标没用」 |
| **凭什么叫它对**（怎么验证的） | 「把程序跑起来问窗口要图标句柄，返回非 0；存成图片看过了，是新图标」 |

**写在哪**

| 场合 | 怎么写 |
| --- | --- |
| **和我的对话里** | 每次汇报都带「为什么」，不能只报结果 |
| **项目更新日志的「计划」块** | 写为什么做这件事 |
| **项目更新日志的「实际做了」块** | 写为什么这么改、踩了什么坑、怎么绕过去的 |
| **项目更新日志的「怎么验证」块** | 写凭什么叫它是对的（跑了什么、看到什么） |

**反过来，不要这样**

- ❌ 只写「已完成 / 已修复」，不说原因，也不说验证方式。
- ❌ 用一堆专业名词糊过去，让我这个不懂代码的人看不懂。
- ❌ 说「应该没问题」—— 没验证就说没验证，别猜。

## 规范三：犯错止损（连错就停，别越错越起劲）

**一句话**：AI 犯错不怕，怕的是同一个坑摔三跤还在原地打转。本规范给「疯狂连环犯错」上硬闸。

**三条铁律**

| 条 | 规矩 | 怎么算违反 |
| --- | --- | --- |
| ① 连错即停 | 同一个错误第 **3 次**出现，立刻停止当前操作 | 已经停下还在换汤不换药地重试 |
| ② 重试必换思路 | 每次重试前，必须先说清「**这次和上次哪里不一样**」 | 说不出差别就动手重试 |
| ③ 停下如实报告 | 触发①后，报告：试了什么 / 错在哪 / 我猜该查什么，**等用户决定**，不许自己硬闯 | 停了不报告、或报告完不看用户回复继续干 |

**为什么是 3 次**：第 1 次可能是手滑，第 2 次可能是理解偏差（换个思路还能救），第 3 次还错说明当前这条路走不通——再试就是烧时间。社区 agent 框架的通用做法也是这个量级。

**写在哪**：触发止损时，在对话里明说「触发止损：XX 已连错 3 次」；当轮收工后在《项目更新日志》该条「实际做了」块里补一句止损经过。

**反过来，不要这样**

- ❌ 同一个命令原样重跑，指望「这次运气好」。
- ❌ 报错信息还没读完就开改。
- ❌ 停下之后说「我再试最后一次」——止损就是止损。

## 规范五：打包和临时的文件有自己的地盘

**一句话**：打包工具、打包输出、临时文件夹、干活脚本**一律放进 调试工具\ 文件夹**，别散在项目根层。给哪个项目干活，就在哪个项目根下建一个（没有就建）。**子文件夹和脚本用英文名**——中文路径在命令行会乱码（规范四）。

| 放什么 | 目录名（英文） |
| --- | --- |
| 打包产物（exe） | build-output |
| 打包工作区 | build-tmp |
| spec 文件 | build-spec |
| 运行临时 | run-tmp |
| 干活的 .ps1 / .py 脚本 | scripts |

**怎么算违反**：把 PyInstaller 的 --distpath/--workpath 指到项目根层，或在根层留散装临时目录。
